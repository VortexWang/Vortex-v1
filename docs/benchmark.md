# 转发基准（ENG-T36）

脚本：`scripts/bench/netns-bench.sh`；节点进程：`engine/cmd/vxbench-node`。

## 拓扑

```
客户端 vxb-c ──1 Gbps── 转发节点 vxb-n ──1 Gbps── 目标 vxb-t
10.201.1.2           10.201.1.1 | 10.201.2.1          10.201.2.2
```

- 三个网络命名空间，两段 veth；每段两个方向都用 tbf 限速（`RATE`，默认 1 Gbps）。
- **直连基准**：客户端经节点的内核路由直接访问目标上的 iperf3，路径与限速相同，不经过引擎。
- **直接转发**：客户端访问节点上引擎的监听 `10.201.1.1:15201`（TCP 与 UDP 同端口），引擎转发到目标 `10.201.2.2:5201`。
- 引擎由模拟 Agent 驱动，规则为执行点，持有运行授权、速率与连接份额、计费授权，目标网段按组放开（SEC-011）。**正式的计量与门控全程生效**：每次拷贝都经过令牌桶与计费预扣，结束时核对计量字节与计费授权消耗。

## 参数

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `WARMUP` / `DURATION` / `RUNS` / `PARALLEL` | 60 / 300 / 3 / 16 | 需求 13.2 节：16 条并发连接、预热 60 秒、测试 300 秒、三次取中位数 |
| `RATE` | `1gbit` | 每段限速；`none` 表示不限速（用于观察引擎自身上限） |
| `UDP_RATE` / `UDP_LEN` / `UDP_DURATION` | `100M` / 1200 / 60 | NFR-005；需求未规定 UDP 时长 |
| `CHECK` | 1 | 按 NFR-001（≥ 700 Mbps 且 ≥ 直连 70%）与 NFR-005（丢包 ≤ 0.1%）判定，不通过时退出码为 1 |
| `OUT` | `bench-results/<UTC 时间>` | 每次运行的 iperf3 JSON、引擎统计 `engine-stats.json`、环境 `env.txt`、汇总 `summary.md` |

需要 root、iproute2（含 tc）、iperf3、python3、Go。CI 的 `netns-bench` 作业以短时长（预热 3 秒、测试 15 秒、一次）执行同一脚本做冒烟判定（ENGR-005）。

## 与 13.2 节环境的差异

开发机与 CI 不是 13.2 节规定的环境：转发节点不独享 4 vCPU（开发机共 2 vCPU，客户端、目标、iperf3 与引擎共享），各段为同一台机器上的 veth（RTT 远小于 2 ms、无丢包）。因此这里的结果只用于 M0 退出判定与回归比较；**正式验收须在 13.2 节环境中用同一脚本、正式参数重新测量**，并保存配置与命令。

## M0 测量结果（2026-10-31，开发机）

环境：内核 6.18、2 vCPU（客户端、节点、目标三个命名空间与四个进程共享）、iperf3 3.16、Go 1.24.7；代码 a09f842（脚本仅增加了丢包定位与 UDP 缓冲参数，引擎代码相同）。

### NFR-001 直接转发（正式参数：16 连接、预热 60 秒、测试 300 秒、三次）

| | 第 1 次 | 第 2 次 | 第 3 次 | 中位数 |
| --- | --- | --- | --- | --- |
| 直连（Mbps） | 955 | 956 | 955 | 955 |
| 直接转发（Mbps） | 954 | 955 | 954 | **954**（直连的 99.9%） |

**通过**（≥ 700 Mbps 且 ≥ 70%）。1 Gbps 限速下瓶颈是链路本身而不是引擎。引擎计量上行 131,124,879,933 字节、下行 9,027 字节，计费授权消耗 131,124,888,960 字节，与两者之和一字节不差；整个 21 分钟运行占用 CPU 用户态 46 s、内核态 196 s，最大 RSS 10.5 MiB，退出时 goroutine 只剩 2 个（运行时自身）。

不限速时（参考，不是验收项；预热 5 秒、测试 30 秒、一次）：直连 27.5 Gbps，直接转发 14.4 Gbps（计量与门控生效），说明在 1 Gbps 链路上引擎有一个数量级以上的余量。

### NFR-005 UDP（1,200 字节、100 Mbps、每次 60 秒、三次）

| 目标端接收缓冲 | 直连丢包（各次 / 中位数） | 直接转发丢包（各次 / 中位数） |
| --- | --- | --- |
| 系统默认 208 KiB | 0.132 / 0.049 / 0.083 → 0.083% | 0.529 / 0.090 / 0.189 → **0.189%** |
| 4 MiB（`UDP_WINDOW=4M`，现为默认） | 0 / 0 / 0 | 0 / 0 / 0 → **0%** |

**通过**，附带说明：使用系统默认缓冲时中位数 0.189%，超过 0.1%。按命名空间的计数器核对，**全部丢包都发生在目标端 iperf3 的接收缓冲溢出**（`RcvbufErrors`），转发节点、客户端与各段限速队列均为 0，引擎没有丢弃任何数据报（直连同样有 0.08% 的目标端溢出）。原因是 2 vCPU 上四个进程争用 CPU：目标端 iperf3 被抢占期间到达的数据报超出 208 KiB 缓冲；经过引擎时多一次调度，到达更成簇，溢出更多。13.2 节环境中目标与转发节点不在同一台机器上，这一因素不存在；因此基准把两端 socket 缓冲设为 4 MiB，并在汇总中逐项列出丢包位置，任何发生在被测路径上的丢包都会单独显示。正式验收时应在 13.2 节环境中复测，并保留默认缓冲的一组结果作对照。

引擎计量 UDP 上行 2,249,970,350 字节（3 × 60 s × 100 Mbps 的理论值 2.25 × 10⁹），计费授权消耗与计量之和一致。
